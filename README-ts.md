# Domo — TypeScript stack

The TypeScript + Electron re-platform of Domo (see [DESIGN.md](DESIGN.md) §13
for the migration plan and rationale). It runs beside the Swift code during the
migration and shares the **same wire protocol and on-disk layout**, so the two
implementations interoperate and are cross-tested.

## Layout

```
packages/
  protocol/      @domo/protocol      canonical JSON, Ed25519 identity, Capability/Intent/Grant,
                                     rule keys, PathUtil, Challenge, DomoConnection  (twin of DomoProtocol)
  transport/     @domo/transport     Connection seam, NDJSON+LineRPC, Unix socket, WebSocket (ws) +
                                     SPKI pinning, E2EChannel (X25519+Ed25519+HKDF+ChaCha20-Poly1305)
  broker-core/   @domo/broker-core   Broker, BrokerStore, MCPSession → signed intents  (twin of DomoBrokerCore)
  device-core/   @domo/device-core   DeviceAgent, PolicyEngine, FileOps, Executor + SBPL, AuditLog,
                                     BlessedTools, GoalsLibrary, identity/key stores  (twin of DomoDeviceCore)
apps/
  broker/        domo-broker  CLI daemon + provisioner subcommands (Linux hosting target)
  mcp/           domo-mcp     stdio↔broker MCP shim for Claude Code
  device/        domo-device  headless device runner (--policy) for tests
  desktop/       Electron app: device-core in the main process; tray, approval windows,
                 Goals/Rules/Audit/Settings UI (visual direction from docs/mockups/audit-mockups.html)
fixtures/        golden conformance vectors, GENERATED BY the Swift code (see below)
e2e/             full-stack scenarios booting real broker + device processes
```

## Build & test

```
npm install
npx tsc -b                 # typecheck + build every package/app
npx vitest run             # all tests (unit + golden vectors + E2E)
npx vitest run packages/protocol     # just the golden-vector conformance
npx vitest run e2e                   # just the full-stack scenarios
```

## Golden vectors (the cross-language safety net)

`fixtures/*.json` are generated by the Swift implementation — Swift is the
**generator of truth** until it is decommissioned (DESIGN.md §13, Phase T6):

```
swift run domo-vectors --out fixtures
```

The TS test suites assert these byte-for-byte: canonical JSON encoding, intent
& grant signing bytes, rule-key normalization, the E2E channel key schedule +
AEAD framing, connection strings, path canonicalization, and SBPL profiles.

**Note on signatures:** CryptoKit's Ed25519 signing is *randomized* (Apple adds
entropy), so signature *bytes* differ run to run. Conformance for signatures is
therefore cross-*verification* — a Swift-made signature verifies in TS and vice
versa — while the *signed bytes* (canonical JSON) are asserted to be identical.
The `sbpl.json` fixture embeds `$HOME`, so its byte-parity assertions only run
on the machine that generated it.

## Mixed-stack E2E matrix

`e2e/e2e.test.ts` runs every scenario in up to three configurations:

- TS broker + TS device (always)
- TS broker + **Swift** device (when `.build/debug` exists — `swift build`)
- **Swift** broker + TS device (when `.build/debug` exists)

The mixed configurations are the proof that the wire contract is honored across
implementations. Build the Swift side (`swift build`) before running E2E to
exercise them; otherwise only the TS/TS row runs.

## Running the desktop app

```
npm run --workspace @domo/desktop build   # tsc + copy renderer assets
npm run --workspace @domo/desktop start   # launch Electron
```

The Electron main process **is** the device agent (runs `@domo/device-core`
in-process). The renderer is sandboxed (`contextIsolation` on, `nodeIntegration`
off, `sandbox` on, strict CSP, no remote content); the approval window renders
only the view model derived from the *verified* canonical intent.
